# Eric 的秘密菜园：产品与 vgpu 探索 Scope R1

**状态：** 长期方向基线；不是已经激活的施工计划。  
**日期：** 2026-09-02

## 1. 这个项目是干什么的

Eric 的秘密菜园同时承担两件事，但优先级明确：

1. **它首先是给 Eric 玩的小菜园。** 操作短、反馈直接、没有惩罚性失败，植物真的会被播种、照料、长大和收获。
2. **它其次是一个小而真实的 WebGPU / vgpu 试验场。** 新渲染技术必须落在合理的菜园情景里，并产生孩子看得见的效果；不允许把脱离产品的 shader demo 堆进主场景。

它不是水晶花园的缩小复制品，也不是通用 3D 引擎。它要做的是：

> 把接近水晶花园单屏级别的视觉与优化投入，集中到一个很小、很完整、每平方米都有内容的可旋转菜园模型中。

成功不以“用了多少 GPU 技术”衡量，而以三件事衡量：

- Eric 能在几分钟内理解并完成一次照料循环；
- 菜园的材质、光、风、生长和天气形成统一的生命感；
- 试验结果能够明确判断是否值得反哺水晶花园。

## 2. 不变的产品契约

现有核心循环保留：

**播种 → 浇水 → 生长 → 必要时赶走小虫 → 成熟 → 收菜 → 看统计表**

产品层保持以下边界：

- 必要操作维持在三个工具加一个主动作以内；
- 缺水或有虫只暂停生长，不死亡、不扣资源；
- 每关保持短小，学习内容藏在统计和观察里，不把游戏做成作业；
- 手机、平板和普通电脑都应能完成完整流程；
- 存档保存游戏语义，不保存任何 GPU 资源或渲染器内部状态；
- 新视觉不能让 UI、点击目标或任务反馈变得难认。

## 3. 世界形态：一个高密度单屏菜园

主场景保持为一个可旋转、可缩放的 **garden diorama**。不扩成多地图，不引入人物自由行走。场景由六类情景载体组成：

| 载体 | 在菜园中的理由 | 可承担的技术与视觉内容 | R1 状态 |
| --- | --- | --- | --- |
| **A. 中央菜畦** | 原本的任务发生地 | 程序土壤、湿润扩散、植物生长、点击选择 | 基础必需 |
| **B. 外围草地与野花带** | 菜地自然需要边缘生态 | vegetation instancing、GPU 风场、密度与 LOD | 首轮必需 |
| **C. 矮栅栏、石路与极小结构物** | 给菜园边界，也给光影提供竖直表面 | 静态 geometry、阴影、材质、render bundle | 首轮精简加入 |
| **D. 天空与天气层** | 现有关卡已经有晴、多云、微风、太阳雨 | 天空、日照、云影、风、雨 | 首轮精简加入 |
| **E. 花草与昆虫角** | 花会吸引蝴蝶、蜜蜂和瓢虫 | billboard/mesh instancing、粒子、访客图鉴 | 后续选项 |
| **F. 雨水角** | 雨水桶和浅水盆可解释浇水与水面 | 波纹、折射、ping-pong/compute | 后续选项 |

### R1 首轮世界基线

首轮只建立：

- 中央菜畦；
- 一圈草地、少量野花和石板路；
- 低矮木栅栏；
- 极简天空、日光、风和云影。

昆虫角、雨水角、完整工具棚都必须在阶段评审后再选，不因技术上能做就自动进入范围。

## 4. 视觉方向与预算使用

视觉目标不是堆多边形，而是让一个小地方持续有生命感。优先顺序为：

1. **轮廓与可读性：** 作物一眼能认，生长阶段有清晰区别；
2. **运动：** 草、叶片、玉米、云影和雨有不同节奏；
3. **光与材质：** 土壤干湿、受光与背光、天气变化可信；
4. **空间布景：** 栅栏、石路、野花和小道具形成完整边界；
5. **细节密度：** 在前四项稳定后再增加粒子、小虫或水面细节。

美术与工程预算可以达到水晶花园的单屏量级，但世界面积和系统数量不得随之膨胀。

## 5. 渲染架构

### 5.1 vgpu 与 WebGPU 的关系

vgpu 是 WebGPU 之上的 TypeScript / WGSL 工具层，不是另一块并列的 GPU。目标架构是：

- **vgpu 是 WebGPU 主路径的默认接口；**
- vgpu 暂时没有覆盖的能力，可以通过一个受控的原生 WebGPU 适配层实现；
- 原生调用必须复用同一个设备、资源生命周期和帧调度，不能另建第二套渲染世界；
- 业务或场景模块不得散落直接的 `navigator.gpu`、`GPUDevice` 或原生 pass 操作。

原生逃生口解决的是“vgpu 暂时未封装的一个缺口”，不是让工程长期同时维护两套 API 风格。

### 5.2 双渲染器不是双场景树

过渡期保留两个实现：

```text
DOM / CSS UI
      │
Game model（播种、浇水、生长、虫害、收获、存档）
      │
Renderer-neutral scene snapshot
      │
GardenRenderer interface
      ├── Canvas2DRenderer   兼容回退 + 现状参考
      └── VgpuRenderer       WebGPU 主路径
            └── RawWebGPUBridge（唯一原生逃生口）
```

规则：

- 同一时刻只启用一个 renderer；
- 两个 renderer 消费同一份游戏状态和场景快照；
- 不复制游戏逻辑，不维护两套植物状态；
- Canvas 2D 在 WebGPU 路径达到功能与交互等价前不删除；
- 不在首轮引入 Three.js。若以后确实需要成熟的模型、骨骼或 glTF 管线，再单独评估；不得先形成 vgpu 与 Three.js 两套 scene graph。

### 5.3 输出仍然是静态站

源码可以在 Phase 0 引入 TypeScript、Vite、固定版本的 vgpu 和 WGSL 构建支持，但生产物仍应是可直接托管的静态 HTML/CSS/JS 资源：

- 无后端；
- 无服务器存档；
- 无运行时密钥；
- 部署平台只负责静态发布。

### 5.4 建议的目标源码结构

目录在真正开工时按需要创建，不预先铺空壳：

```text
src/
├── app/                 # 启动、能力探测、renderer 选择
├── game/                # 纯游戏状态、关卡、存档与动作
├── scene/               # renderer-neutral 场景快照与坐标
├── render/
│   ├── contract.ts      # GardenRenderer 接口
│   ├── canvas2d/        # 旧路径适配与回退
│   └── vgpu/
│       ├── runtime/     # 单一 Gpu、surface、frame loop、资源生命周期
│       ├── passes/      # sky、world、vegetation、effects
│       ├── materials/   # soil、plant、wood、water 等
│       ├── shaders/     # WGSL 模块
│       └── raw/         # 唯一原生 WebGPU 逃生口
├── ui/                  # DOM UI 与输入适配
└── diagnostics/         # FPS、frame time、draw/instance/resource 统计

tests/
├── game/
├── render-mock/
├── render-node/
└── browser/
```

## 6. 技术试验必须由情景承载

| 试验 | 主载体 | 玩家看见的结果 | 主要判断问题 |
| --- | --- | --- | --- |
| 程序土壤 | 菜畦 | 土壤颗粒、垄沟、干湿差异 | 少贴图能否得到稳定材质质量 |
| 湿润场 | 浇水与菜畦 | 水落下后湿斑扩散并逐渐变干 | ping-pong/compute 是否值得进入产品 |
| 连续生长 | 作物 | 离散关卡状态之间平滑展开 | GPU 参数化能否减少模型阶段数量 |
| vegetation instancing | 草地与野花 | 大量草花形成完整边缘 | 500/1500/4000 实例下的成本与组织方式 |
| GPU 风场 | 草、花和作物 | 不同植物按刚度产生不同摆动 | 单一风场能否替代逐对象 CPU 动画 |
| 日光与云影 | 全场、栅栏和地面 | 天气真正改变场景而非只换 emoji | 低成本光照变化是否足够有生命感 |
| 静态 bundle | 栅栏、石路、固定道具 | 玩家无直接感知，场景更稳定 | 静态部分能否降低每帧提交成本 |
| 昆虫/花粉 | 花草角 | 蝴蝶、蜜蜂、瓢虫或花粉 | instancing 足够还是需要 compute |
| 水面与波纹 | 雨水角 | 水滴、波纹和反光 | 模拟收益是否配得上复杂度 |
| Node/mock 渲染测试 | renderer 本身 | 玩家无直接感知 | 是否能形成可复现的 shader 与像素回归 |

技术试验只有在以下至少一项成立时才进入主路径：

- 明显提高孩子可感知的画面或反馈；
- 明显降低稳定达到该效果的资源或维护成本；
- 形成可迁移到水晶花园的可靠结论。

## 7. 分阶段路线

### Phase 0 — 渲染地基

只建立可替换渲染层，不重做世界：

- 固定并锁定一个验收过的 vgpu 版本；
- TypeScript/WGSL 构建；
- `GardenRenderer`、单一 frame-loop owner、能力探测和 Canvas 回退；
- vgpu browser、Node 和 mock 的最小三角/读回验证；
- 诊断面板记录 FPS、frame time、draw calls、instances 和资源数。

**阶段出口：** WebGPU 与回退路径都能加载同一游戏状态；不改变现有关卡语义。

### Phase 1 — 中央菜畦

- 菜畦几何和程序土壤；
- 现有六种作物的最低可认版本；
- 四阶段逻辑映射为连续视觉生长；
- 浇水落点和湿润视觉；
- 点击/触控选择与旧路径等价。

**阶段出口：** 第一关可完整播种、浇水、生长、处理虫害和收获；Canvas 回退仍可玩。

### Phase 2 — 菜园边缘与天气

- 石路、草地、少量野花和矮栅栏；
- vegetation instancing 和 GPU 风；
- 简单天空、日照与云影；
- 静态 bundle、DPR 控制和实例负载档位。

**阶段出口：** 小菜园形成完整场景；性能数据能够比较 500/1500/4000 实例。

### Phase 3 — 选择一个扩展载体

只选一个方向进入当前施工：

- **3A 花草昆虫角：** 菜园访客、billboard/mesh instancing、必要时 compute；
- **3B 雨水角：** 雨水桶、浅水盆、波纹与水面；
- **3C 小工具棚与完整天气：** 更丰富的竖直结构、阴影、材质和天气表现。

**阶段出口：** 该载体既能作为孩子可理解的场景内容，也完成一项明确的技术结论。

### Phase 4 — 反哺评审

逐项判断：

- 哪些 shader、数据布局、实例系统或测试可以迁移；
- 哪些只适合这个小场景；
- vgpu 是否继续作为独立主渲染层；
- Canvas 回退是否继续保留；
- 是否值得在水晶花园中进行受限共存试验。

Phase 4 是评审，不自动触发水晶花园施工。

## 8. 初始性能与验证口径

Phase 0 先测基线，再把数字转成硬门槛。起步时使用以下统一口径：

- DPR 默认限制在 `1–2`；
- vegetation 使用 `500 / 1500 / 4000` 三个负载档；
- 交互目标优先 60 FPS，选定支持设备上的持续低于 30 FPS 视为需要降级；
- 每帧禁止逐实例创建对象、buffer、texture、pipeline 或 bind group；
- 动态 uniform/instance 数据原位更新，静态资源复用；
- 同时记录平均帧时、长帧、draw/pass 数、实例数、资源创建数和构建体积；
- 视觉验收必须包含 WebGPU 主路径和 Canvas 回退；
- 无 WebGPU、设备丢失或初始化失败时应回退，而不是留下空白画布。

这些是施工方向，不是为了让尚未建立基线的 Phase 0 先被一堆数字堵死。

## 9. 明确不做

除非以后另立 Scope，不进入本项目：

- 水晶花园式经济、背包、邮件、邮购、复杂制作链；
- 多地图、室内空间、山洞、自由行走和 NPC；
- 账号、云存档、多人或后台服务；
- 惩罚性枯死、付费资源或复杂资源管理；
- 为展示技术而加入与菜园无关的传送门、能量场或抽象粒子墙；
- 首轮全面依赖 Three.js、完整 PBR 资产管线或大型 scene framework；
- 一次性把 Canvas 旧路径推倒重写；
- 在没有产品需要时先做 compute、复杂水模拟或后处理栈。

## 10. 已定与待选

### 已定

- 产品优先，研发试验必须由合理菜园情景承载；
- 单屏高密度 diorama，而非扩大世界；
- vgpu 为 WebGPU 主接口，原生 WebGPU 只有受控逃生口；
- 单一游戏状态、单一帧 owner、同一时刻单一 renderer；
- Canvas 2D 先作为回退和参考保留；
- 首轮世界采用菜畦 + 草花边缘 + 矮栅栏 + 简单天空；
- 分阶段完成，每阶段后再决定是否继续扩展。

### 待选

- Phase 3 首先做昆虫角、雨水角还是小工具棚；
- 首轮主要基准设备；
- 植物美术偏更绘本化还是更 low-poly；
- Canvas 回退的最终保留周期；
- 哪一项成熟结果值得进入水晶花园的独立验证。
